## MedXpert-五、图书馆管理思路

> 搭建知识库只是第一步，**持续运营才是图书馆的价值所在**。

### 5.1 分类体系设计

**三层分类法**（推荐）：

```
图书馆/
  L1-领域/           # 第一层：大领域
    L2-主题/         # 第二层：具体主题
      L3-类型/       # 第三层：文档类型
        具体文件.md
```

示例：
```
my-library/
  01-法规/
    01-国内/
      GMP/
        GMP-2014.md
        GMP-2025.md
      NMPA/
        注册办法.md
    02-国际/
      FDA/
        21-CFR-820.md
      MDR/
        EU-MDR-2017.md
  02-产品/
    产品A/
      技术文档/
      测试报告/
    产品B/
  03-标准/
    ISO/
      ISO-13485.md
    ASTM/
  04-学习笔记/
    大模型/
    器械知识/
  05-运营/
    流程/
    模板/
```

**分类原则**：
1. **MECE**：相互独立、完全穷尽（一个文件只属于一个分类）
2. **不超过 3 层**：太深了找不到
3. **数字前缀**：`01-` `02-` 控制排序
4. **预留扩展位**：不要把分类填满，留出增长空间

### 5.2 知识录入流程

```
原始资料 → [1.筛选] → [2.脱敏] → [3.结构化] → [4.摘要] → [5.入库] → [6.索引更新]
```

| 步骤 | 做什么 | 谁做 | 工具 |
|------|--------|------|------|
| 1. 筛选 | 判断是否值得入库 | 人 | - |
| 2. 脱敏 | 去除敏感信息（公司名、人名、证号） | 人/模型 | 正则+模型检查 |
| 3. 结构化 | 转成 Markdown，加标题层级 | 模型 | Ollama 摘要+格式化 |
| 4. 摘要 | 生成 200 字摘要 | 模型 | Ollama |
| 5. 入库 | 放到正确分类目录 | 人 | 文件系统 |
| 6. 索引更新 | 更新索引文件 | 脚本 | 自动化 |

**脱敏很重要**：外部资料入库前必须脱敏。客户/第三方资料涉及公司名、人名、证号的，写入前必须替换。用模型辅助脱敏：

```python
DESENSITIZE_PROMPT = """请对以下内容进行脱敏处理：
1. 公司名 → [公司A]、[公司B]
2. 人名 → [张三]、[李四]
3. 证件号/账号 → [证号]
4. 地址 → [地址]
保留技术内容和结构，只替换敏感信息。

内容：
{content}"""
```

### 5.3 知识更新与版本管理

**版本管理三件套**：

1. **Git 版本控制**（推荐）
   ```bash
   cd my-library
   git init
   git add .
   git commit -m "新增：GMP 2025版解读"
   ```
   - 每次更新都有记录，可回溯
   - 支持分支（比如"试验性知识"分支）

2. **文件头标注元信息**
   ```markdown
   ---
   title: GMP 2025版与2014版主要差异
   source: NMPA 官网
   date_added: 2026-08-18
   last_updated: 2026-08-18
   version: 1.0
   status: 已核实
   tags: [GMP, 法规, 对比]
   ---
   ```

3. **变更日志**
   ```
   changelog.md
   - 2026-08-18: 新增 GMP 2025版解读；更新 ISO 13485 条款索引
   - 2026-08-15: 初始导入 30 份法规文档
   ```

### 5.4 知识检索与问答

**三层检索策略**：

| 层级 | 方法 | 适用场景 |
|------|------|---------|
| L1 索引浏览 | 看 `00-index.md` | 知道大概有什么 |
| L2 关键词搜索 | `grep -r "关键词" my-library/` | 找具体内容 |
| L3 语义问答 | Ollama + RAG | 提问获取综合答案 |

**问答质量提升技巧**：
- 提问时指定范围：`"根据 01-法规 目录下的内容回答..."`
- 要求引用来源：`"回答时标注信息来自哪个文件"`
- 多轮追问：第一次回答不够精确时，追问细化

### 5.5 知识质量控制

**定期健康检查（Lint）**：

| 检查项 | 方法 | 频率 |
|--------|------|------|
| 过时知识 | 对比最新法规/标准 | 每月 |
| 矛盾内容 | 模型交叉检查 | 每月 |
| 孤儿文件 | 索引中未引用的文件 | 每周 |
| 重复内容 | 模型查重 | 每月 |
| 格式规范 | 脚本检查元信息完整性 | 每次入库 |

**用模型做健康检查**：
```python
HEALTH_CHECK_PROMPT = """请检查以下知识库内容是否存在问题：
1. 是否有过时信息（与最新法规/标准不符）
2. 是否有自相矛盾的内容
3. 是否有未完成的占位内容
4. 摘要是否准确反映正文

知识库索引：
{index}

请列出发现的问题。"""
```

### 5.6 图书馆运营节奏

| 节奏 | 做什么 | 耗时 |
|------|--------|------|
| **每日** | 新知识入库、摘要生成 | 10 分钟 |
| **每周** | 索引更新、孤儿文件清理 | 30 分钟 |
| **每月** | 知识质量检查、过时内容更新 | 1-2 小时 |
| **每季** | 分类体系评审、知识库结构优化 | 2-3 小时 |

> **💡 核心技巧：把重活留到晚上让模型自己干（夜间批量任务）**
>
> 白天你只需要**把文件丢进对应目录**（1 分钟），剩下的批量摘要、结构化、入库、索引更新**全部交给模型在夜间自动跑**——第二天醒来，图书馆已经帮你把新知识整理好了。
>
> 实现方式：
> - **Windows 任务计划程序**：`schtasks /create /tn "夜间摘要" /tr "python quickstart.py summarize" /sc daily /st 23:00`
> - **或 Linux cron**：`0 23 * * * cd /path/to/library && python quickstart.py summarize`
> - **低配电脑正好利用夜间空闲**：白天上班电脑闲着也是闲着，晚上让它干活，不占用你白天任何时间
> - **运行提醒**：批量任务前确认 `OLLAMA_KEEP_ALIVE` 已设置，避免模型反复加载

**核心原则**：
1. **知识是活的**——不更新的知识库就是死水
2. **质量 > 数量**——50 份精炼文档 > 500 份堆砌文件
3. **人机协作**——人负责判断和筛选，模型负责处理和摘要
4. **持续迭代**——分类体系不是一次定死的，随知识增长而调整

### 5.7 文件管理规范（命名 / 格式 / 生命周期 / 备份）

**命名规范（三选一，全库统一）**：

| 类型 | 格式 | 示例 |
|------|------|------|
| 按主题 | `主题-名称.md` | `GMP-2025版解读.md` |
| 按日期 | `YYYY-MM-DD-名称.md` | `2026-08-18-注册新规.md` |
| 按版本 | `名称-vN.N.N.md` | `ISO13485-解读-v1.2.md` |

> 命名三原则：**小写连字符优先**（AI 和人都好读）、**不含特殊字符**（`/ \ : * ? " < > |`）、**前缀控制排序**（`01-`/`02-` 或日期）。

**Markdown 格式规范（全库统一）**：

| 元素 | 规范 | 示例 |
|------|------|------|
| 标题层级 | H1 一个 / H2 分节 / H3 细节 | `# 文档名` → `## 章节` → `### 小节` |
| 元信息 | 文件头 YAML frontmatter | 见下 |
| 表格 | 表格优先于列表（AI 好解析） | `\| 列1 \| 列2 \|` |
| 代码 | 标注语言 | ` ```python ` |
| 引用来源 | 文末统一"参考来源"节 | `## 参考来源` |
| 图片 | 放 `assets/` 子目录，相对路径引用 | `![图](assets/xxx.png)` |

**frontmatter 元信息模板**（每个入库文件必备）：
```markdown
---
title: GMP 2025版与2014版主要差异
source: NMPA 官网（公开）
date_added: 2026-08-18
last_updated: 2026-08-18
version: 1.0
status: 已核实        # 草稿/已核实/已过时/已归档
level: 公开           # 公开/内部/机密
tags: [GMP, 法规, 对比]
summary: 一句话摘要
---
```

**文件生命周期**：
```
新建(草稿) → 入库(已核实) → 定期维护 → 过时(标注) → 归档(移入 99-归档/)
```

| 阶段 | 动作 | 谁 |
|------|------|-----|
| 新建 | 按模板创建，标 `status: 草稿` | 人/模型 |
| 入库 | 摘要+脱敏+元信息完整后标 `已核实` | 模型+人确认 |
| 维护 | 月度检查，过时标 `已过时` | 模型体检 |
| 归档 | 移入 `99-归档/`（不删除，留痕） | 人 |

**备份策略（三份原则）**：
1. **本地主库**：`my-library/`（Git 版本控制）
2. **异地备份**：网盘（微云/坚果云）每周自动同步
3. **冷备份**：每月导出 zip 存移动硬盘/云存储
> 备份 = 防删错 + 防硬盘坏 + 防勒索病毒，三份不嫌多。

**文件有跟踪（谁在何时改了什么，一清二楚）**：

| 跟踪手段 | 做法 | 看到什么 |
|---------|------|---------|
| **Git 全历史** | 每次修改提交，可回溯任意版本 | `git log` 看全部变更历史，`git diff` 看单次改动 |
| **变更日志** | 每次入库/更新在 `changelog.md` 记一笔 | 按日期倒序的变更清单 |
| **元信息戳** | frontmatter 的 `last_updated` + `version` | 每个文件最后更新时间与版本 |
| **审计日志** | 批量操作（摘要/入库）由脚本记录操作日志 | 谁跑了什么命令、处理了哪些文件 |
| **访问留痕** | 远程访问时 DSH/Ollama 日志记录请求 | 什么时间谁访问了模型 |

**Git 跟踪快速上手**：
```bash
cd my-library
git init
git add .
git commit -m "初始导入"
# 之后每次改动：
git add -A && git commit -m "新增：XXX"
# 看历史：
git log --oneline
# 找回误删文件：
git checkout <commit-hash> -- <文件名>
```
> 配合远程仓库（GitHub 私有库/公司 GitLab）可异地同步 + 云端留痕，**双重保险**。
